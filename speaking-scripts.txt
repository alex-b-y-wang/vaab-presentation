Imagine a therapist who needs an app for care plans. They know what to record, such as patient goals and review notes. But turning those needs into software still takes technical help.

Our aim was to make that step easier. With VAAB, users describe their needs in plain language, answer questions when needed, and agree on a plan before the app is built.

Slide 05 — How do users stay involved?
Speaker: Yan | Target: 40 seconds | 72 words

Users can step in at three points.

Before the build, they check each task and approve the full plan. This gives them a chance to correct the system’s understanding.

During the build, they can follow progress and stop the process.

After the build, they review the preview and ask for changes, such as a new title. VAAB targets the files that need to change.

Let’s see this flow in a care-planning example.

提示（不朗读）：
1. 生成前：检查任务并批准计划
2. 生成中：查看进度或停止
3. 生成后：检查预览并提出修改
4. 衔接：下面展示实际流程

Slide 07 — How the agent works
Speaker: Zhijia | Target: 74 seconds | 128 words

You’ve seen the user’s steps. Now, let’s look at the AI process behind them.

We use LangGraph to manage six roles. The Clarifier asks questions when more detail is needed. The Planner turns the request into tasks. The user checks the plan before the build starts.

The Executor builds one file at a time. Reflection checks the code and whether the task is complete. Early builds had code errors, so we added these checks. Failed tasks can retry, with limits to stop endless loops.

For an existing app, the Editor plans changes to the files that need them. This supports small edits, like the title change in our demo. If an edit still fails after retries, the earlier file is restored.

Finally, the system gives a short summary.

提示（不朗读）：
1. 从 demo 转入 AI 流程；Clarifier 与 Planner
2. 用户确认后才开始生成
3. Executor 与 Reflection：为什么需要检查
4. 有限重试，避免循环不止
5. Editor 与 demo 标题修改对应；失败恢复；最终总结

Source (not spoken): Group02.pdf §§11.1, 11.5; Appendix E

Slide 08 — How the backend supports users
Speaker: Zhen | Target: 70 seconds | 120 words

The backend connects this AI process to the user’s screen and saved work.

First, the Express API checks the login token and makes sure the app belongs to that user.

During the build, it sends progress updates to the screen. We use server-sent events, or S S E, so users can follow the work as it happens.

The database saves the chat, completed files, and the file used to start the app. In our tests, refreshing the page brought the saved app back into the preview. Stopping a build also kept the last completed version.

This helps users return to saved work. One limit remains: after a server restart, the system cannot yet restore a build that was still running.

提示（不朗读）：
1. 连接 AI、用户界面和保存的结果；登录与项目归属
2. SSE 的作用：让用户跟上实时进度
3. 保存完成结果；刷新恢复；停止保留上一完成版本
4. 明确边界：服务器重启不能恢复仍在运行的任务

Source (not spoken): Group02.pdf §§8.4, 9.3, 11.3, 11.6; Appendix D

Slide 09 — What did we test?
Speaker: Youxi | Target: 73 seconds | 129 words

We tested whether these parts worked together, from an agreed plan to a saved app.

A run with a real model API produced four files. We checked the saved files and viewed the result in the browser.

One earlier problem was a blank preview, or losing it after a refresh. We fixed how the saved files and starting file were loaded. Browser checks then showed that the form returned after a refresh.

We also checked that simulated release and feedback records were saved. Some repeat tests used fixed mock responses. This let us repeat selected checks without calling the real model each time.

The results support the workflow we tested locally. They do not show that every request will work, or that the app is ready for clinical use.

提示（不朗读）：
1. 真实 API：四个文件；保存和浏览器检查
2. 问题—修复—验证：刷新后预览恢复
3. 模拟发布/反馈记录；解释 mock 为重复测试提供固定输入
4. 结果支持已测试本地流程，不能推广到所有请求或临床使用

Source (not spoken): Group02.pdf §§10.4, 10.9, 14.4; Appendix F

Slide 10 — User evaluation
Speaker: Haoyang | Target: 45 seconds | 86 words

We also asked users to try the system. Five occupational therapy staff took part in the final study.

All five completed app creation on their own. In the needs discussion, three worked alone and two needed help.

Four gave positive ratings for matching their needs and for preview clarity. Three rated control positively. Editing and progress each received two positive ratings.

This suggests that understanding the result was easier than managing the process. Clearer guidance is our next priority. With five participants, these are early findings.

提示（不朗读）：
1. 五人最终研究；独立完成与需要帮助的区别
2. 需求匹配和预览清晰度各4人正面评价
3. 控制感3人正面评价
4. 编辑与进度各2人正面评价
5. 解释结果与改进方向；强调小样本初步发现

Source (not spoken): Group02.pdf §§14.1–14.5; Appendix A. Positive rating = 4 or 5 on a five-point scale.
