Slide 05 — How do users stay involved?
Speaker: Yan | Target: 41 seconds

Users can step in at three points. Before the first build, they check each task and approve the full plan. During the build, they can see progress and stop the process. After the build, they check the app and ask for changes, such as a new form title. VAAB targets the files that need to change. We also tested how clear these steps were to users. The demo shows this flow.

Slide 07 — How the agent works
Speaker: Zhijia | Target: 70 seconds

Here is how the AI process works. We use LangGraph to manage six roles. For a new app, the system first asks questions, then makes a plan. The user checks the tasks and approves the plan before code generation starts. The system builds one file at a time, then checks the code and the task result. Early builds had code errors, so we added these checks. Failed tasks can retry, but the loops have limits. For an existing app, an editor checks the new request and plans the changes. This avoids a full rebuild when it is not needed. If an edit still fails after retries, the system restores the earlier file. It ends with a short summary.

动画提示（不朗读）：
1. Clarifier 与 Planner
2. 用户确认后才开始生成
3. Executor 与 Reflection
4. 检查失败：有限重试或重新规划
5. 现有应用的 Editor 与最终总结

Source (not spoken): Group02.pdf §§11.1, 11.5; Appendix E

Slide 08 — How the backend supports users
Speaker: Zhen | Target: 70 seconds

The backend links the AI process to the user screen. First, the Express API checks the login token and makes sure the app belongs to that user. Next, it sends progress updates while the app is being built. We use server-sent events, or S S E, for this. The database saves the chat, completed files, and the file used to start the app. In our tests, a page refresh restored the saved app in the preview. Work that was stopped did not replace the last completed version. This supports recovery after a page refresh. A server restart is a different case. The current system cannot yet restore an active build after a restart.

动画提示（不朗读）：
1. 验证登录与项目归属
2. SSE 推送进度
3. 保存结果与页面刷新恢复
4. 边界：服务器重启后不能恢复活跃任务

Source (not spoken): Group02.pdf §§8.4, 9.3, 11.3, 11.6; Appendix D

Slide 09 — What did we test?
Speaker: Youxi | Target: 70 seconds

We checked the full path from an agreed plan to a saved app. A real model API run produced four files, which the backend saved. We also checked the result in the browser. One earlier problem was a blank preview, or losing it after a refresh. We addressed this by loading the saved files and the app's starting file. Browser checks showed that the form returned after a refresh. We also checked that the simulated release and feedback records were saved. Some repeat tests used fixed mock responses. These checks support the tested local workflow. They do not prove that every request will work, or that the app is ready for real clinical use.

动画提示（不朗读）：
1. 真实 API：生成并保存四个文件
2. 修复空白预览，并验证刷新恢复
3. 模拟发布与反馈记录
4. 测试范围：部分使用 mock，尚非临床就绪

Source (not spoken): Group02.pdf §§10.4, 10.9, 14.4; Appendix F

Slide 10 — User evaluation
Speaker: Haoyang | Target: 38 seconds

Five occupational therapy staff took part in the final study. All five did the app-creation task on their own. For the needs discussion, three worked alone and two needed help. Four gave positive ratings for intent match and preview clarity. Three felt in control. Two gave positive ratings for editing and progress. The results show promise, but clearer guidance is still needed. This was a small study.

动画提示（不朗读）：
1. 五位参与者与任务完成情况
2. 需求匹配与预览清晰度：4/5
3. 控制感：3/5
4. 编辑与进度：2/5
5. 小样本有潜力，但仍需更清晰的引导

Source (not spoken): Group02.pdf §§14.1–14.5; Appendix A. Positive rating = 4 or 5 on a five-point scale.
